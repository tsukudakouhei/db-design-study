エンティティ設計 — 中間テーブルは「1つの関係」につき1つ

多対多には中間テーブル

「フリーランスはスキルを複数持つ」「案件もスキルを複数要求する」——多対多の関係は、関係そのものを1行とするテーブル（中間テーブル）で表す。skill1, skill2, skill3 と列を並べる設計は最初の罠。

最重要: 1つの中間テーブル = 1つの関係

最初の設計では (skill_id, freelance_id, job_id) の3方向テーブルを作ってしまった。これは「人がスキルを持つ」と「案件がスキルを要る」という独立した2つの関係の同居。

田中さんが TypeScript を登録したい。でもまだどの案件にも応募していない。3方向テーブルに入れる行の job_id は…何を入れる？ NULL？ → 片方しか存在しないケースで必ず破綻する。
指摘を受けて freelancer_skills と job_skills の2テーブルに自力で分解できた（後のラウンド4で判明: これは第4正規形の判断）。

その他の教訓

  • 要件に登場する登場人物（企業）をテーブルとして落とさないと、「この企業の案件一覧」が出せない。要件文とテーブル一覧を突き合わせる
  • 全テーブルに主キー（id）があるか指差し確認。無いと他所から参照できない
  • カラム名のタイポは後から直すのが大変（参照するコード全部が壊れる）。DDLを書く段階で見直す

履歴とイベント — 上書きは過去を消す

行を積む vs 上書きする

原則: UPDATE で上書きすると過去が消える。履歴が欲しいものは INSERT で行を積む。

応募ステータス（応募中→書類通過→面談→成約）の変化を追いたい → ステータス変更のたびにレコードを作る、という発想は正しい。ただし置き場所が肝心。

エンティティとイベントは別テーブル

応募(applications)テーブル自身に履歴行を積むと、「田中×案件A」の行が3行に。応募者数を COUNT すると水増しされ、二重応募禁止の UNIQUE 制約も張れず、contracts が指す application_id はどの行か分からなくなる。

応募というモノ（1つ）と状態が変わったという出来事（複数）は数が違う。数が違うものは別テーブル:

applications                     … 応募1件につき1行（現在の status はここ）
application_status_histories     … id, application_id, status, changed_at

履歴は「直近の親」に繋ぐ

履歴を freelance_id に繋ぐと、案件Aと案件Bに同時応募中のとき「この書類通過はどっちの応募？」が特定できない。応募を飛び越えて人に繋いではいけない。
失敗シナリオを見て application_id への付け替えを自力で答えられた。

細かい定石

  • 日時カラム名は「出来事＋at」（changed_at / applied_at）。date は何の日付か読めない
  • 設計の正解は SQL ではなく業務が決める。契約単価の改定 → 「契約を巻き直す」業務なら新契約行＋previous_contract_id、「同一契約の改定」なら単価履歴テーブル。どちらも defensible

インデックス理論 — DBは何もしなければ全行読む

フルスキャンとインデックス

DBは指示がなければ1行目から最終行まで全部読む（フルスキャン）。それを避ける道具がインデックス＝「その列の値で並べた目次」。

紙の辞書で「リンゴ」を引くとき1ページ目からめくる人はいない。五十音順と知っているから一発で近くを開ける。それが目次（B-tree インデックス）。
ルール1: 主キーには自動でインデックスが付く。それ以外の列には自分で張らない限り目次は存在しない。
ルール2: タダではない。行を書くたび目次も並べ直すので、張るほど書き込みが遅くなる。効かない目次は張らない。

どこに張るか = 「大きいテーブル」の「一番絞れる列」

「経験3年以上」は50万行中25万行該当（半分） → 目次があっても大差ない。「skill_id = TypeScript」は50万→5千行（100分の1） → 劇的に効く。この「どれだけ一気に絞れるか」を選択性と呼ぶ。

複合インデックスは電話帳

電話帳は「姓→名」の順に並んでいるから「佐藤さんの中の太郎さん」が一発で引ける。(skill_id, 経験年数) は「スキルごとに並べ、その中を経験年数順に並べた」目次。
CREATE INDEX idx_fs_skill_years ON freelancer_skills (skill_id, 経験年数);
--                                   ↑ ＝で絞る列が先、範囲(>=)で絞る列が後。順番が命

テーブルの太り方は予言できる

法則: 1対Nの線が1本増えるたび、N側は「親の数×平均個数」で太る。中間・履歴テーブルは本体の数倍〜数十倍に育つ。ER図の「Nの端」を見れば将来重くなる場所が読める。
テーブル行数の目安
freelancers（本体）10万
freelancer_skills（中間）50万〜100万
applications100万
application_status_histories（履歴）300万+

created_at / updated_at は全テーブルに最初から

「登録が新しい順」という要件が来た瞬間、日時カラムが無いと詰む。後から「いつ作られたか」は復元できない。

正規化 — 1つの事実は1箇所にだけ書く

更新アノマリー（正規化が防ぐ事故）

「JOINが面倒だから jobs にも company_name を持たせよう」→ 社名は companies に1箇所＋jobs に100箇所の計101箇所に。社名変更で jobs 側の更新が漏れると、DBに新旧2つの社名が併存。どちらが正か、DBのどこにも書かれていない——真実の在り処（Source of Truth）がDBの外（当時の設計者の頭の中）に漏れ出す。これが「面倒」ではなく「事故」。
正規化の一言定義: 1つの事実は、1箇所にだけ書く。
実務の判定質問: 「この列は、この行の主キーに付随する事実か？ それとも別の誰かの事実のコピーか？」

自分の判断に付いていた名前

やったこと教科書上の名前
skill1, skill2, skill3 と列を並べず別テーブル＋中間に第1正規形（繰り返し項目の排除）
jobs への company_name コピーを却下第3正規形（キー以外への依存の排除）
履歴から freelance_id を排除（application 経由で辿れる）第3正規形（辿れる事実の重複排除）
3方向テーブルを2つの中間テーブルに分解第4正規形（独立した多対多の分離）

逆回転: あえてコピーが正しいケース（スナップショット）

判断基準: 元データが変わったとき——追従すべきなら、コピーは事故（正規化する）。当時のまま凍結すべきなら、コピーこそ正しい（スナップショット）。
  • ❌ applications に freelancer_name → 改名に追従すべき情報。JOINで取る
  • ⭕ 注文明細の unit_price、発行済み見積書の宛先社名・単価 → 過去の合意の記録。凍結が正しい
  • kintone のルックアップフィールドはまさに「コピーして持つ」設計。マスタ変更に追従しないのは、この意図的スナップショット（と、事故の両面がある）

実機で実証 — EXPLAIN は嘘をつかない

SQLite・freelancer_skills 100万行の実データで計測（2026-07-19）。手順は README.md 参照。

実行計画の読み方は2単語でいい

|--SCAN fs                                     ← 😱 全行読み（100万行）
|--SEARCH f USING INTEGER PRIMARY KEY          ← 目次で一発
`--USE TEMP B-TREE FOR ORDER BY                ← 並び替え用の目次をその場で毎回作成
SCAN = 全行読み ／ SEARCH ... USING INDEX = 目次で短絡。この2つを見分ければ実行計画は半分読めた。

「張る」と「使われる」は別イベント

CREATE INDEX したのに実行計画は SCAN のまま、時間も変わらない。→ プランナが統計情報を知らないと目次を使ってくれない。ANALYZE を流したら採用され、61ms → 19ms（約3倍）になった。「インデックスが効かない」時はまず統計を疑う。

左端プレフィックスの実証

複合主キー (freelancer_id, skill_id) の自動インデックスがあるのに、skill_id からの検索には使われない——同じテーブルへの2方向の質問で実証:

WHERE freelancer_id = 42  → SEARCH ... USING INDEX (freelancer_id=?)  ✅
WHERE skill_id = 1        → SCAN                                       ❌

skill_id=1 の行は全員のブロックに1行ずつ散らばっているから、どこか1箇所を開いても全部は見つからない。複合インデックスは左の列から順にしか効かない。主キーは1テーブル1つだが、インデックスは何本でも張れる——中間テーブルの「PK (a,b) ＋ 逆順 (b,a) の2本構成」は頻出パターン。

最適解は計測が決める

CREATE INDEX skill_id ON freelancer_skills (skill_id, freelancer_id); を自力で書き、教科書解 (skill_id, 経験年数) と実測勝負して引き分け（19ms vs 21ms）。範囲列「経験3年以上」は該当73%で選択性が低く、絞り込みはほぼ等号列が稼いでいたため。しかも自作の方が他の検索に使い回せて汎用性は上。
教訓: 「教科書的な最適」と「実測」は別物。最後は EXPLAIN と計測で決める。範囲列は選択性が低ければ複合に入れても効かない。

ORDER BY にはタイブレーク

ORDER BY created_at DESC だけだと同値内の順序が不定で実行のたびに変わる（ページネーションで人がダブる事故の原因）。定石は ORDER BY created_at DESC, id DESC。

⚡ 迷ったとき30秒チートシート

  • 多対多？ → 中間テーブル。ただし1テーブル1関係。関係の属性（経験年数）は中間テーブルへ
  • 履歴が欲しい？ → 上書きせず行を積む。エンティティとイベントは別テーブル。履歴は直近の親に繋ぐ
  • コピーを持ちたい？ → 元が変わったら追従すべき？（→持つな、JOINしろ）凍結すべき？（→スナップショット、持ってよし）
  • 遅い？ → EXPLAIN で SCAN を探す → 大きいテーブルの一番絞れる列に INDEX → ＝が先・範囲が後 → ANALYZE → 再計測
  • ER図を描いたら → Nの端のテーブルは本体の数十倍に太ると予言しておく
  • 全テーブル共通 → id（主キー）、created_at / updated_at、ORDER BY にはタイブレーク列
  • 設計に迷ったら → 正解は SQL ではなく業務が決める。失敗シナリオを1つ作って設計にぶつけてみる
